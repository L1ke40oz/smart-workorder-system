# 智能工单处理系统 · 需求与实施计划

## 需求依据与当前状态

依据 SPEC v1.1（已于 2026-10-20 完整阅读）。本文不替代原始 SPEC；以下阶段描述是验收目标，实际完成范围见开发记录。

截至第 2 轮：基础业务、Gemini 分析与确认、历史工单向量检索和参考建议代码已实现。基础流程经过 MySQL 与 Android 模拟器验证；智能模块经过本地供应商接口测试，尚未配置真实 Gemini / 硅基流动密钥，因此不宣称真实模型联通或准确率已验证。

## 必须遵守的技术与业务约束

- Android 使用 Java、XML Layout、MVVM、ViewModel、LiveData、Retrofit、RecyclerView；不改用 Kotlin 业务代码或 Compose。保留 API 24 最低版本，Gradle Kotlin DSL 可继续使用。
- 同一个 App 提供普通用户和管理员两个角色入口。角色和数据访问权限由后端校验，不能只依靠界面隐藏。
- Android 仅通过后端 REST API 访问业务数据，不直连 MySQL；模型密钥放在后端环境配置中。
- 普通用户只能查看自己的工单；管理员可查看全部工单，并负责接单、填写处理结果和完成工单。
- 完整保留用户原始描述，AI 生成的摘要、标签等单独保存，不能覆盖原文。
- 大模型分类只允许：设备故障、网络问题、软件问题、账号问题、其他问题。
- 紧急程度只允许：一般、较急、紧急。不确定的设备名称和地点允许为空，不强行补充事实。
- 后端校验 AI 结构化输出；分析成功不代表已经正式创建工单，用户确认后才创建。
- 状态主流程为：待处理 → 处理中 → 已完成。实际处理结果必须由管理员填写，AI 不自动完成工单。
- 已关闭属于可选增强功能；语音、图片、OCR 等不阻塞基础闭环与 RAG。

## 分阶段实施与验收

### 阶段一：基础业务闭环

按照 SPEC 第 19 节，先完成不依赖外部 AI 服务的基础流程。该阶段验收不代表 P0 全部完成，AI 相关 P0 项在阶段二补齐。

计划内容：

- 建立 Spring Boot REST API、MySQL 数据模型和基本权限控制。
- 实现普通用户注册、用户和管理员登录、登录态与角色首页。
- 普通用户使用文字提交工单，查看自己的工单列表、详情和历史记录。
- 管理员查看全部工单及详情，接单后进入处理中，填写处理结果后完成工单。
- 用户查看最新状态与实际处理结果。
- 提供基础数量统计及类别统计，优先支持状态和类别筛选。
- Android 按界面、ViewModel、Repository、网络与数据模型分层。

验收场景：用户注册并登录 → 创建文字工单 → 管理员登录并找到该工单 → 接单 → 填写结果并完成 → 原用户查看结果；另一个普通用户无法访问该工单。

### 阶段二：LLM 智能受理，补齐 P0

计划内容：

- 后端调用模型接口，将原始描述映射为固定 JSON 字段：`category`、`deviceName`、`location`、`priority`、`tags`、`summary`。
- 校验类别、优先级、字段类型及长度，处理超时、无效 JSON 和缺失字段。
- Android 展示 AI 分析结果供用户确认，然后正式提交工单。
- 持久化原始描述与最终确认的结构化字段，防止确认按钮重复触发创建。
- 外部服务不可用时清晰展示失败并允许重试；如需人工填写作为降级方案，应明确标识，不能把规则或模拟结果显示为模型分析。

验收场景：提交打印机故障原文 → 显示合法的分析结果 → 确认后仅创建一张工单 → 详情同时显示原文和结构化信息；模型出错时不偷偷创建工单。

### 阶段三：RAG 辅助处理，完成 P1

计划内容：

- 接入文本 embedding 与向量检索，具体服务根据可用环境确定。
- 将已完成工单及其实际解决方案、FAQ 等纳入知识库，保留来源和关联工单编号。
- 工单完成后更新相应知识索引，避免同一工单重复入库。
- 管理员详情中展示相关案例、来源、匹配度及模型生成的处理参考建议。
- 仅使用有权限的参考数据；无匹配结果、服务异常时明确展示对应状态。
- RAG 建议不代替管理员实际处理结果，不自动改变工单状态。

验收场景：完成一个打印机故障工单 → 为相似新工单检索到该案例 → 管理员查看案例及参考建议 → 管理员自行填写结果并完成新工单。

### 阶段四：增强功能

根据进度实现系统语音识别、故障图片上传与查看、图表统计、用户确认关闭。OCR、多模态、Rerank 和复杂检索策略放在基础功能稳定之后。

## 建议的核心数据与接口边界

以下用于指导后续设计，具体字段和路径在实现时确定。

| 领域 | 需要保存的信息或承担的职责 |
| --- | --- |
| 用户 | 账号、密码哈希、角色、基础个人信息；普通注册不允许自行获得管理员权限 |
| 工单 | 工单编号、提交用户、原始描述、分类、设备、地点、紧急程度、标签、摘要、状态、时间、处理人和实际结果 |
| 分析结果 | 用户确认前的结构化预览，不直接等同于正式工单 |
| 状态管理 | 后端限制合法状态变化，校验操作角色与处理结果，并处理重复或并发操作 |
| 工单查询 | 用户查询按当前身份限定范围；管理员查询可按状态、类别等筛选 |
| 数据统计 | 管理员查看数量、各状态数量、类别分布 |
| 知识记录 | 内容、来源、关联已完成工单、向量索引标识 |
| 图片附件 | 所属工单、文件位置、上传者等，后续增加文件类型、大小及访问权限校验 |

## 已确认的信息与后续配置

1. **后端与运行环境**：用户确认从零创建 `backend/`，无已有项目数据库，后续可使用自有 VPS。本轮已通过独立临时 MySQL 实例验证，保留 H2 dev 模式便于直接启动。
2. **模型服务**：用户指定 Gemini 与硅基流动 BAAI embedding。已实现 Gemini 原生 REST 与 `BAAI/bge-m3` 适配，真实模型名和两家密钥待配置；不要将密钥写入开发记录。
3. **自主选型**：没有指定 ORM、向量数据库或界面。采用 JPA + Flyway，以及可持久化的嵌入式 Lucene HNSW 向量索引；Android 使用中文浅色界面，不使用 emoji 装饰。
4. **后续范围**：真实模型服务联调、实际案例检索质量验证、VPS 部署，以及语音和图片等 P2 增强功能。P3 仍为可选，不影响基础业务运行。
